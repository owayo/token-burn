# レート制限

アカウントの使用量の枠が埋まったときに token-burn が後続のタスクをどう止めるか、上限に達して終わったタスクをどう分類するかを説明します。閾値は[基本設定](configuration.ja.md#基本設定)の `rate_limit_threshold` です。

## 閾値の判定

`rate_limit_threshold` は 2 つの経路で判定します。タスクの実行中は、Claude Code の stream-json に流れる `rate_limit_event` をリアルタイムに監視し、閾値を超えたら後続のタスクを止めます。[ai-usage 連携](configuration.ja.md#ai-usage-連携任意)を有効にしている場合は、さらに各タスクの完了後に、該当する `(profile, provider)` の `weekly` と `five_hour` の `used_percent` から、エージェントの実際の使用率をこの閾値と照らし直します。こちらは `claude` と `codex` の両方に効くので、リアルタイムの監視が無い `codex` でも止まります。

どちらの経路も、**どう**止めるかは閾値を超えた枠の周期で決めます。週次枠は実行のデッドラインと周期が同じなので、実行を恒久的に止めます。短い枠 (`five_hour` や、`kind:"daily"` として報告される 24 時間枠) は、その枠がリセットされるまでの一時停止にとどめます。再開の時刻を過ぎたワーカーは、使用率を確かめ直してから次のタスクに進みます。周期はスロット名ではなく `kind` から求めます。24 時間枠を `five_hour` のスロットで返すプロバイダが実際にあるためです。リセット時刻が無いとき、ありえない値 (その枠の 1 周期より先) のときは、一時停止ではなく恒久停止になります。再開の時刻が実行のデッドラインより後のときも恒久停止になりますが、ai-usage 連携があれば、手動リセットに備えてデッドラインまで待ちます。

ai-usage 連携での判定には、ai-usage の共有キャッシュ (既定 120 秒) を通さず `--refresh` で取り直した値を使います。キャッシュの値では、手動リセットの直後でもリセット前の使用率が返り得るためです。実行中のアカウントだけを `--profile` と `--only` で取り直すので、ほかのアカウントには問い合わせません。`--refresh` を知らない古い ai-usage では、従来どおりの取得に戻ります (この場合、手動リセットによる早めの再開は行いません)。

## 手動リセットでの早めの再開

Claude (claude.ai の Settings > Usage の "Reset for free") と Codex (banked reset) では、使用量の枠を任意のタイミングで回復できます。一時停止の再開時刻は、止まった時点の観測から見積もった時刻にすぎません。ai-usage 連携があれば、token-burn はリセット時刻を実データから都度調べ、手動リセットで枠が戻ったらその時刻を待たずに再開します。

一時停止中は、モニターが約 30 秒ごとに実行中のアカウントの使用率を取り直します。最初の取得は、止まった原因の観測から 35 秒が過ぎるまで待ちます。それより前に取った使用率は観測より前の値かもしれず、回復を示せないためです。前の実行から持ち越した一時停止は、見つけたらすぐ確かめます。止まった原因の枠が止まった時点の半分以下まで (かつ 10 ポイント以上) 下がり、どの枠も閾値未満になったら、一時停止を解除します。待機中のワーカーは 1 秒以内にそれを読み、使用率を確かめ直してから次のタスクを始めます。少し下がっただけでは解除しません。API とウェブの使用量ページの値は丸めや反映の遅れでずれ、拒否は使用率と別の理由でも起きるためです。止まった時点の使用率が 10% 未満なら 10 ポイント下がることがないので、モニターは問い合わせず、早めに再開できない旨を通知に出します。

実行の開始時も実データで決めます。5 時間枠が閾値以上ならそのリセットまで一時停止した状態で始め、週次枠が閾値以上ならタスクを 1 件も始めません。使用率を確認できない (ai-usage の取得に失敗した、アカウントのエラーが報告された) ときも、タスクを始めません。前の実行で 5 時間枠に拒否されて中断したセッションがあっても、その後に枠が戻っていれば保留せずに始めます。待たずに始めたことは早めの再開として記録するので、始めた直後にまた拒否された場合も、次の段落の扱いになります。

早めに再開した直後にまた API に拒否された場合、その一時停止は ai-usage の値と API の値を比べる方法では解除しません。ai-usage が実際に動かしているのと別のアカウントを見ている構成では、解除と拒否を繰り返してキューを失敗で使い切るためです。

ai-usage 連携が無い構成では使用率を調べる手段が無いので、見積もった時刻まで待ちます。

## 停止と一時停止

待機中のワーカーは毎秒 pause file を読み直します。別のワーカーが一時停止を延長すると、残り時間・枠名・停止理由も延長後の観測に合わせます。延長後の再開時刻がデッドライン以降なら、元の再開時刻を待たずに恒久停止します。待機中に pause file が読めなくなった場合や壊れた場合も停止します。モニターの再開時刻の通知も、一時停止の変更に合わせて更新します。

- **5 時間枠の枯渇では実行全体を捨てない**: 停止は枠の周期で 2 種類に分かれます。週次枠（デッドラインと同じ周期）が閾値に触れたら恒久停止ですが、5 時間枠のように待てば回復する枠なら**その枠のリセットまでの一時停止**にとどめ、時刻を過ぎたワーカーは残りのタスクを続行します。ここで恒久停止すると、週次リセットまでの実行余力を丸ごと捨てることになります。実ログでは、5 時間枠は閾値に触れた数分後にリセットされ、そのとき週次枠は 43%、デッドラインまで 4 時間 52 分残っていました。待つとデッドラインを越える場合、リセット時刻が読めない場合は恒久停止します。一時停止から再開する直前には実データで使用率を確かめ直します。再検証が一時停止を延長した場合は、延長後の時刻にも再検証します。再検証が失敗したら、stop file を書けなくてもそのワーカーは止まります
- **停止判定とタスク取得は不可分**: ワーカーは「停止していないか確かめる」と「キューからタスクを取る」を 1 つのロックの下で行います。2 段に分かれていた頃は、その隙間に別のワーカーが停止を発行すると、停止後にタスクが開始されていました
- **ai-usage 使用率ゲート**: ai-usage 連携時、各タスク完了後に該当 agent の実使用率（weekly / five_hour）を枠ごとに確認し、`rate_limit_threshold` 以上なら後続タスクを停止または一時停止。stream-json のリアルタイム監視が無い codex でも実使用率で確実に止まり、取得失敗時は fail-closed で安全側に倒す
- **閾値ちょうどでも止める**: 使用率は % の小数 2 桁に丸めてから閾値と比べます。浮動小数では `0.57 * 100` が `56.99999999999999` になり、閾値 57 の実行が `57% used` と表示しながら止まりませんでした（閾値 29・57・58 で起きていた）
- **自動停止は実行を止める枠だけで判定**: 停止判定に使うのは `unifiedWindows` の 5 時間枠 / 7 日枠の使用率で、月次の追加課金枠（`overage`）の使用率では停止しません。実データでは 5 時間枠が 13% でも `rateLimitType:"overage"` / `utilization:1.03` の警告が届き、これを閾値と比べて全タスクが止まっていました。停止行には判定した枠の名前・使用率・**その枠自身の**リセット時刻を出し、`[5h 13% / 7d 54%]` の形で実測値を併記します。追加課金枠の警告は `(overage, no auto-stop)` として表示のみ行います
- **レート制限通知**: 使用率の警告、リクエスト拒否、overage（超過枠）の状態・リセット時刻（警告時と拒否時にも表示）、および `allowed_warning` でサーバー側が通過した警告閾値（例: `warning at 90%`）を表示し、ローカル閾値超過時に後続タスクを停止（7 日枠なら恒久停止、5 時間枠ならその枠のリセットまでの一時停止。stop file の作成が ENOSPC・権限不足等で失敗した場合は握り潰さず、停止シグナルが生成されない旨を出力に明示）

## 上限に達したタスクの分類

- **上限到達の判定**: `resets 2:30am` のような分を含む時刻表記や、`You've hit your session limit` / `You've hit your org's monthly spend limit` といった上限到達メッセージを、リトライ可能なプロバイダエラーではなくレート制限として扱う（リトライしても回復しないため）
- **リセット時刻の日付表示**: リセットが翌日以降になる場合は `MM/DD HH:MM` 形式で日付も表示（`seven_day` 枠や超過枠は最大 1 か月先になるため、時刻だけだと当日中に回復するように誤読される）
- **接続断の再試行扱い**: `API Error: Connection closed mid-response` のように HTTP ステータスを伴わない一時的な接続障害は恒久エラーではなく再試行可能として扱い、ワーカーを止めずに次のターゲットへ進む（次回実行で再処理される）

レート制限で切られた Claude Code のタスクは、次の実行で続きから再開できます。[中断セッションの再開](usage.ja.md#中断セッションの再開)を参照してください。
